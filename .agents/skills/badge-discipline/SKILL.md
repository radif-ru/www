# Дисциплина бейджей

Читай перед добавлением или изменением бейджей в `README.md`.

## Зачем

Бейджи — первое, что видит человек, открывший репозиторий. Бейдж без логотипа,
с битой ссылкой или с устаревшим числом работает против репозитория: читатель
делает вывод не о бейдже, а о качестве работы автора.

## Правила

### 1. Проверяй `curl` каждый URL, а не «на глаз»

shields.io при неизвестном имени логотипа **не отдаёт ошибку** — он молча
рисует бейдж без логотипа. Код ответа 200 ничего не доказывает.

Проверка обоих условий сразу — код ответа и наличие встроенного логотипа:

```bash
grep -oE 'https://img\.shields\.io/[^)]+' README.md | while read -r u; do
  svg=$(curl -s "$u")
  printf '%s' "$svg" | grep -q 'image/svg+xml;base64' && s="LOGO-OK" || s="NO-LOGO"
  printf '%-8s %s\n' "$s" "$u"
done
```

В выдаче не должно остаться ни одного `NO-LOGO`.

### 2. Имена логотипов — из simple-icons, с оглядкой на переименования

Источник имён — [simpleicons.org](https://simpleicons.org/). Набор меняется:
иконки переименовывают и удаляют. Проверено в этом репозитории — работает
`logo=css`, `logo=html5`, `logo=googlechrome`, `logo=w3schools`; **не**
работает `logo=css3`, `logo=w3c`, `logo=accessibleicon`, `logo=wcag`.

Быстрая проверка кандидата:

```bash
for l in css css3 w3c accessibleicon; do
  curl -s "https://img.shields.io/badge/test-x-blue?logo=$l" \
    | grep -q 'image/svg+xml;base64' && echo "OK   $l" || echo "FAIL $l"
done
```

### 3. Группируй по смыслу, а не в одну простыню

Строки разделяются пустой строкой в markdown. Порядок групп в этом
репозитории: **CI и качество** → **стек** → **принципы** → **GitHub-метрики**.
Читатель сканирует группы, а не 30 бейджей подряд.

### 4. Бренд-цвета

Цвет бейджа — официальный цвет технологии (HTML5 `E34F26`, Docker `2496ED`,
Nginx `009639`, PostgreSQL `336791`). Для собственных смысловых бейджей —
палитра: зелёный `1a7f37` для принципов-инвариантов, синий `0969da` для
нейтральных фактов, фиолетовый `8250df` для безопасности.

### 5. Ссылка бейджа ведёт на доказательство

Бейдж — это утверждение, ссылка — его подтверждение. `CI checks-5` ведёт на
workflow, `coverage gate` — на конфиг с порогом, `submodules` — на раздел
README. Ссылка на главную страницу репозитория вместо конкретного файла —
упущенная возможность.

Осторожно с подстраницами GitHub: `/stargazers` отдаёт 404 при нуле звёзд —
это ловилось `check_links.py` в этом репозитории. Веди на корень репозитория.

### 6. Живые и статические бейджи — разделяй честно

Живые (значение запрашивается при отрисовке): статус CI, доступность сайта,
`stars`, `issues`, `last commit`, `commit activity`, `repo size`, `code size`.

Статические (значение зашито в URL): числа гейтов, версии стека, принципы.
Они меняются **только** правкой README — значит, меняются в том же коммите,
что и сам факт.

Оформляй это пояснением в `<details>`, а не первым абзацем: свёрнутый блок
информирует, развёрнутый — звучит как оправдание.

### 7. Не заявляй бейджем то, чего нет

Бейдж `tests-889` допустим, только если `pytest` действительно собирает 889
тестов. Бейдж `coverage-88%` — только если это выдаёт прогон. Бейдж как
украшение — прямая ложь в самом заметном месте страницы.

## Проверка перед коммитом

```bash
./scripts/preflight.sh          # разметка, мета-данные, форматирование
python3 scripts/check_links.py  # живость ссылок, включая бейджи
```
